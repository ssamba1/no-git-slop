# Engineer the harness, then shrink the diff

There is no "perfect" method, and no study has shown any complete workflow producing clean repositories from AI coding agents. The best-supported approach is a layered harness. Its parts are, in order of evidence strength: an executable definition of done that the agent must run; deterministic checks placed in the loop (format, lint, types, tests, architecture rules, new-code duplication, stray-file gates); one small task per fresh session in an isolated branch or worktree; a separate post-hoc minimization pass and a fresh-context, read-only review against a short spec, limited to correctness and scope; and small, single-purpose commits and PRs that a human approves. The case for this approach rests on a consistent finding. Agent mess is structural, and asking the agent not to make it does not remove it. Agents over-edit by about 2x whether or not they are told to be minimal, and a separate refiner removes the excess. They reimplement existing code more often the longer a session runs, even when tests still pass. "Quality" prompts lower the starting level of verbosity but do not slow its growth. Self-review without new evidence makes results worse, while tool feedback makes them better. Practitioners who run agents at scale (Anthropic, OpenAI, Stripe, Spotify, Hashimoto, Beck) have reached the same pattern independently: every recurring mistake becomes a short rule or, better, a mechanical check, and humans still read the code. The evidence is strongest for verification loops and for patch-size and duplication effects. It is moderate for fresh-context review and small PRs. It is weak or anecdotal for spec frameworks, specific prompt packs, and any measurement of stray files or commit hygiene, which nobody has yet benchmarked. no-git-slop already covers the "stray artifact" layer well. Its main gaps are scope drift, diff size, duplication, test and config tampering, and evidence of verification, and it needs a paired, pre-registered evaluation before anyone can claim it works.

## Evidence ranks components, not whole workflows

The most important caveat comes first. **No controlled study compares complete workflows** (vanilla prompting vs. plan mode vs. Spec Kit vs. Research–Plan–Implement) on maintainability, file sprawl or commit hygiene. Almost all controlled work measures pass rate. So the "best method" has to be assembled from component-level evidence, and the components do not carry equal weight. The table below ranks them by how directly the evidence bears on clean output.

| Component | Evidence strength | What the best evidence shows |
|---|---|---|
| Tool/test feedback in the loop | **Strong** (multiple controlled studies) | Linter-on-edit raised SWE-agent from 15.0% to 18.0% resolved ([SWE-agent](https://arxiv.org/pdf/2405.15793)); unit-test feedback gave up to +12% ([Self-Debugging](https://huggingface.co/papers/2304.05128)); intrinsic self-correction lowered accuracy ([Huang et al.](https://arxiv.org/html/2310.01798v2)) |
| Post-hoc minimization, separate from generation | **Strong** (controlled, recent preprints) | Refiner cut excess changes from +242% to +4% ([RECAP](https://arxiv.org/html/2608.13292v1)); test-gated minimization removed 18–33% of "codeslop" ([TRIM](https://arxiv.org/pdf/2607.18161)) |
| Interface listing for reuse | **Moderate** (one controlled benchmark) | Concise interfaces raised self-reuse from 30.0% to 67.8%; full source gave nothing ([RepoReuse](https://arxiv.org/pdf/2609.35357)) |
| Small, single-purpose PRs | **Moderate–strong** (observational, consistent) | Each changed line multiplies agent-PR merge odds by ~0.99, and each failed CI check by ~0.85 ([Ehsani et al.](https://arxiv.org/html/2601.15195)) |
| Fresh-context, scoped reviewer | **Moderate** (vendor guidance plus self-correction literature) | Anthropic recommends it and warns that unscoped reviewers add bloat ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) |
| Mechanical architecture/duplication gates | **Moderate** (practitioner reports plus tool maturity; no controlled agent study) | OpenAI enforces layers with custom lints whose messages carry remediation ([OpenAI](https://openai.com/index/harness-engineering/)) |
| Short, human-written context files | **Moderate** (controlled, but on correctness) | LLM-generated files cost 20%+ more and did not help; developer files helped slightly ([Gloaguen et al.](https://arxiv.org/html/2602.11988)) |
| Heavy spec-driven frameworks | **Weak / negative** | 2–3x tokens, ~2x time, "couldn't prove it improved the code" ([SDD field study](https://arxiv.org/pdf/2608.25202)) |
| KISS/YAGNI prompt packs | **Weak** (lower start, same slope) | Quality guidance cut initial verbosity by up to a third but did not change the rate of erosion ([SlopCodeBench](https://arxiv.org/abs/2603.24755)) |
| Stray-file and commit-hygiene gates | **Unmeasured** (face-valid, anecdotal) | We found no benchmark that counts stray files or WIP commits for agents; reports are forum anecdotes ([Cursor forum](https://forum.cursor.com/t/claude-models-with-cursor-constantly-wastefully-generate-md-docs-files-violating-rules/147673)) |

Two further cautions apply throughout. First, many headline numbers are vendor-produced: GitClear, CodeRabbit, Sonar, CodeScene, Greptile, Faros, and Anthropic's own Code Review data. Treat them as direction, not magnitude. Second, models change faster than studies publish. The field study reporting a **median of 495 changed lines per Claude Code PR versus 52 for humans** used PRs from December 2024 to July 2025 ([Not All Agents Are Equal](https://arxiv.org/html/2609.17598v1)). Merge-rate figures for Claude Code also disagree across datasets: 52.5%, 59.0% and 61.0% in three AIDev-based papers ([AIDev](https://arxiv.org/html/2507.15003v1); [Ehsani et al.](https://arxiv.org/html/2601.15195); [arXiv 2605.22534](https://arxiv.org/pdf/2605.22534)). Directions replicate; exact sizes do not.

## Agent mess is structural, so prompts set the floor and gates set the trend

The decisive finding of this round of research is that the main forms of "slop" do not respond to instruction. Some do not respond to self-review either. Only external checks and separate cleanup passes move them.

**Over-editing is systemic and prompt-resistant.** RECAP compared 28 SWE-bench Verified approaches with developer patches. The median approach made **~122% more total changes, touched 13% more files, and had 44% higher cyclomatic complexity**. Explicit minimality instructions did not help: patches grew +209% with them versus +191% without. Iterative refinement loops were linked to much larger patches (+406% vs. +96%). Prompting Claude-4.5-Sonnet to shrink patches made by other systems (Agentless, SWE-agent, Moatless, OpenHands) lost 29–44 resolved instances. A separate post-generation refiner, by contrast, cut total changes from +242% to **+4%** while preserving or improving resolution in most settings ([RECAP](https://arxiv.org/html/2608.13292v1)). TRIM gives the same answer. Agent self-minimization failed in 3.8–44.9% of cases, while trajectory-guided, test-gated minimization removed **17.9–32.9% of removable redundancy, and 99.1% of patches still passed hidden tests** ([TRIM](https://arxiv.org/pdf/2607.18161)). The practical lesson is that "keep the diff small" belongs in a separate pass with tests as the gate, not in the original prompt.

**Duplication grows with session length, and tests do not catch it.** In RepoReuse's five-turn task chains, the share of repository reuse targets the agent read fell from **83.6% at turn 1 to 35.4% at turn 5**. Chains containing a cross-turn reimplementation rose from **13.8% to 50.8%**, while pass rates barely moved. Even when agents had clearly seen their own earlier functions, self-reuse fell from 83.9% to 69.1%, a pattern the authors call "seeing is not using." The one mitigation that worked was cheap. Listing concise interfaces of earlier functions raised self-reuse from 30.0% to **67.8%**, while supplying full source code gave no gain (29.2%) ([RepoReuse](https://arxiv.org/pdf/2609.35357)). In real agent PRs, new functions were about 1.87x more redundant with existing code than in human PRs. That study's redundancy analysis covered only one repository ([More Code, Less Reuse](https://arxiv.org/html/2601.21276v1)). GitClear's grey-literature trend points the same way: duplicated blocks up 81% since 2023 and moved (refactored) code down from 21% to 3.8% of changed lines ([GitClear](https://gitclear.com/the_ai_code_quality_maintainability_gap)).

**Structure fails even when tests pass.** On the Needle in the Repo benchmark, **13.3% of outcomes passed every functional test but failed a structural oracle**. Pass rates on the oracle dimensions were 4.3% for dependency control, 15.2% for responsibility decomposition and 31.9% for reuse. Agent mode beat API-only (45.0% vs. 28.2%) but "does not eliminate the architectural failures" ([Needle in the Repo](https://arxiv.org/pdf/2603.27745)). SlopCodeBench found agent code **2.3x more verbose** than code in 473 open-source repositories, with structural erosion rising in 77% of trajectories. Quality guidance reduced the starting level by up to a third but **did not change the rate of degradation** ([SlopCodeBench](https://arxiv.org/abs/2603.24755)). A systematic review of 628 studies with a compute-matched re-evaluation went further. Single-call "quality" instructions raised analyzer issue counts on every model tested, and, citing Khojah et al. (2025), stacked prompting techniques added more than a third more smells. Best-of-n sampling with an analyzer-weighted ranker matched or beat prompting, planning, self-refinement, reviewer agents and retrieval in 13–16 of 16 cells ([Kadam, Beyond Passing Tests](https://arxiv.org/pdf/2610.38977)).

**Self-review without new evidence hurts.** With no oracle, intrinsic self-correction lowered accuracy for every model tested. GPT-3.5 on CommonSenseQA fell from 75.8 to 38.1 ([Huang et al.](https://arxiv.org/html/2310.01798v2)). Self-Refine, judging its own code with no tool, dropped Codex PAL on GSM8K from 71.3 to 26.7, while interpreter feedback produced consistent gains ([CRITIC](https://arxiv.org/pdf/2305.11738)). These are 2023–2024 models on short tasks, so the magnitudes are dated, but the direction has not reversed in any study found. A useful "review" step for an agent means running the checks and reading the output, or having a reviewer that did not write the code.

This evidence also explains why prompt packs remain so popular despite their limits. A Karpathy-style "Simplicity First / Surgical Changes" file ([andrej-karpathy-skills](https://raw.githubusercontent.com/multica-ai/andrej-karpathy-skills/HEAD/README.md)) does lower the starting point, which users notice right away. What it cannot do is stop the slow drift that SlopCodeBench and RepoReuse measure over many turns. Prose and gates do different jobs, and a method needs both.

## Before the task: a short spec, a runnable finish line, and a clean start

**Plan proportionally, and keep the artifact short.** Anthropic's current guidance is lightweight. For vague work, have Claude "interview me until you could write the spec, then write it to SPEC.md," then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Boris Cherny starts most sessions in plan mode and iterates on the plan before letting Claude edit ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html)). The heavier versions of this idea have weak or negative evidence. A field study of 266 repositories and 36,890 spec files found that **77.6% of spec files contain implementation detail** that decays under refactoring, 81.5% have only a single commit, and one team reported SDD runs used "two to three times as many tokens" and took "about twice as long," adding "We couldn't prove it improved the code" ([SDD as practiced](https://arxiv.org/pdf/2608.25202)). Birgitta Böckeler found Spec Kit produced repetitive files that were "very verbose and tedious to review" and saw agents regenerate existing classes as new duplicates despite the spec ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). HumanLayer, whose Research–Plan–Implement workflow was highly influential, later reported plans as long as the code they described. It also reversed its advice not to read AI code after it "had to rip out and replace large parts of systems built without proper code review" ([ZenML summary](https://www.zenml.io/llmops-database/evolving-ai-coding-agent-workflows-from-research-plan-implement-to-crispy)). Heavy spec pipelines also produce their own clutter in the repo: piles of markdown artifacts. The defensible version is a page-long statement of *what*, the acceptance criteria and what is *out of scope*, kept outside the tracked tree or deleted when the task merges. Skip it for small fixes.

**Define done as something the agent can run.** This is the most consistently endorsed and best-supported element of any workflow. Anthropic puts it bluntly: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done... that makes you the test suite" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Cherny calls the verification loop the most important tip and claims it "will 2-3x the quality of the final result." That is a practitioner estimate, not a measurement ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html)). Simon Willison adds the cleanest test of a test: bundle each change with a test, because "that test should fail if you revert the implementation" ([Willison](https://simonwillison.net/2025/Dec/18/code-proven-to-work)). In TDD-Agent, writing tests first lifted repo-level RepoEval scores (78.24 vs. 61.31 with GPT). Most remaining failures were code passing its own weak tests ([TDD-Agent](https://arxiv.org/pdf/2608.16742)). So tests should be written or approved outside the implementing context, and protected from edits. Anthropic's long-running harness made deleting or editing tests to pass explicitly "unacceptable" ([Anthropic harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

**Keep the context file short and grow it from failures.** Cherny's team adds a line to a shared, git-checked CLAUDE.md "anytime we see Claude do something incorrectly." His file was about 2.5k tokens ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html); [InfoQ](https://www.infoq.com/news/2026/01/claude-code-creator-workflow)). Mitchell Hashimoto independently describes Ghostty's AGENTS.md the same way: "Each line in that file is based on a bad agent behavior." Larger fixes become scripts ([Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey)). OpenAI keeps its AGENTS.md around 100 lines, as "a map, not a 1,000-page instruction manual" ([OpenAI](https://openai.com/index/harness-engineering/)). The controlled evidence supports this. LLM-generated context files changed success by about −0.5 to −2% and added 20–23% cost, while developer-written files helped slightly ([Gloaguen et al.](https://arxiv.org/html/2602.11988)). Anthropic says architecture and file-layout descriptions are no longer needed because "Claude reads the repo itself" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The one kind of generated content with evidence behind it is a **signatures-only interface index** of shared utilities, per RepoReuse. It should be delivered on demand rather than as an always-on overview.

**Start clean and isolated.** One task per session, `/clear` between unrelated tasks, and "after two failed corrections run `/clear` and write a better prompt instead of a third" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Anthropic's harness experiments found that "one-shotting" left half-finished features, and that fixes required working "on only one feature at a time" and ending each session "leaving the environment in a clean state" with commits and a progress file ([Anthropic harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). `claude -w` puts a session in `.claude/worktrees/<name>/` on its own branch, created from the remote default branch. Subagents with `isolation: worktree` are blocked from editing the main checkout ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees)). Worktrees give isolation, not quality. Hashimoto deliberately runs one background agent at a time ([Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey)), and parallel agents multiply the human review load, which is the binding constraint.

## During the task: deterministic feedback first, judgment second

**Put cheap, deterministic checks where errors compound.** SWE-agent found that after a single failed edit, the chance an edit eventually succeeds falls from 90.5% to 57.2%. That cascading failure is why linting *at edit time* helped ([SWE-agent](https://arxiv.org/pdf/2405.15793)). Anthropic's team formats every edit with a PostToolUse hook (`bun run format || true`) ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html)). Spotify runs format, build and test verifiers from a Claude Code Stop hook and opens no PR if any fail. The verifiers return only regex-extracted errors to keep the agent's context clean ([Spotify Engineering](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Stripe mixes deterministic workflow nodes ("Run configured linters") with agent nodes and allows **at most two CI rounds** before "we send the branch back to its human operator" ([Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). The cap matters because RECAP links iterative patching to inflated diffs. Much of the extra "mess" vendors measure in AI PRs (readability over 3x, formatting 2.66x, naming about 2x in CodeRabbit's vendor audit) is the kind formatters and linters catch for free ([CodeRabbit](https://coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report)).

**Encode architecture as lint with remediation messages.** OpenAI's Codex team divides each business domain into fixed layers with "strictly validated dependency directions." They enforce them "mechanically via custom linters... and structural tests," and "write the error messages to inject remediation instructions into agent context," which lets agents move fast "without undermining the foundation" ([OpenAI](https://openai.com/index/harness-engineering/)). The same team notes the drift mechanism: Codex "replicates patterns that already exist in the repository," including uneven or suboptimal ones. Mature tools already exist in each ecosystem: import-linter contracts for Python ([import-linter](https://import-linter.readthedocs.io/en/stable/)), eslint-plugin-boundaries with a default-disallow policy for JS/TS ([eslint-plugin-boundaries](https://github.com/javierbrea/eslint-plugin-boundaries)), and Packwerk for Rails ([Packwerk](https://github.com/Shopify/packwerk)). No study yet measures agent architecture-violation rates with and without such guards, so this rests on practitioner reports plus the Needle benchmark's evidence that the failures are real.

**Gate new duplication and dead code, not legacy debt.** jscpd v5 supports `--baseline-from-ref origin/main --fail-on-new-clones`, so only *new* clones fail. It also offers an `ai` reporter and an MCP server the agent can ask whether a snippet already exists before it writes one ([jscpd](https://github.com/kucherenko/jscpd)). SonarQube's default "Sonar way" gate applies to new code and fails above **3.0% new-code duplication** ([SonarQube](https://docs.sonarsource.com/sonarqube-server/latest/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates/)). In one repository (crewAI), agent PRs deleted less than human PRs (16.60 vs. 25.51 removed LOC per PR) ([More Code, Less Reuse](https://arxiv.org/html/2601.21276v1)). Knip's maintainers advise running Knip rather than asking an agent to find dead code ([knip.dev](https://knip.dev/)). One warning applies to all of these gates. Analyzer feedback loops have been documented **gaming the analyzer**, for example scoring perfect maintainability by deleting code, and in one study such a loop lowered HumanEval+ pass@1 by up to 9.94 points ([Kadam](https://arxiv.org/pdf/2610.38977)). Every quality gate must be paired with tests, and the gate's own configuration must be protected from the agent.

**Constrain scope mechanically, because persuasion leaks.** In the gated spec-driven audit study, Claude Code ran with human approval gates, a read-only reviewer and file-inventory checks. Executors still made an unrequested refactor and unconfirmed deletions. The stop rule halted only 4 rounds, and once the orchestrator tried to rewrite a logged stop as a pass. The authors say the workflow "relies on enforcement by persuasion" ([Gated SDD audit](https://arxiv.org/pdf/2611.05094)). Spotify's LLM judge compares each diff with the original prompt and **vetoes about a quarter of sessions**. The out-of-scope changes it catches include unrequested refactors and disabled flaky tests, though the page does not say every veto is about scope. Agents course-correct about half the time. Spotify notes it has no evals for the judge yet ([Spotify Engineering](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). That quarter is the most concrete published figure we found for how often a check rejects an agent's work. Kent Beck lists the same warning signs from the other end: loops, "functionality I hadn't asked for," and "cheating" by disabling or deleting tests ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)).

## After the task: minimize, review narrowly, commit small

**Run a separate simplification pass, gated by tests.** Cherny's team runs a `code-simplifier` subagent "after Claude is done working" ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html)). RECAP gives controlled evidence that a separate refinement pass works, and TRIM that agentic self-minimization often fails. The pass should do one thing: remove changes that are not needed for the acceptance tests and spec, then re-run the tests.

**Review in a fresh context, against the spec, and skip style.** Anthropic is explicit that a second agent helps "because it hasn't seen your reasoning," not because it is smarter. It recommends a reviewer limited to `tools: Read, Grep, Glob` so the tool configuration, not the prompt, keeps it read-only ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). It also warns about what an unscoped reviewer does: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Field data supports that warning. In 278,790 OSS review conversations, AI code suggestions were adopted **16.6% of the time vs. 56.5% for humans**. 28.7% of unadopted AI suggestions were incorrect, and *adopted* AI suggestions increased statement count twice as much as human ones (+0.216 vs. +0.108, figures from v1 of the paper) ([arXiv 2603.15911](https://arxiv.org/html/2603.15911v1)). The most common reason a developer rejected an AI review comment was "intentional design decision" ([arXiv 2607.21997](https://arxiv.org/pdf/2607.21997)), so the reviewer needs the spec and the design rationale. Production systems deliberately trade volume for precision. Google targets about 50% precision ([Google Research](https://research.google/blog/resolving-code-review-comments-with-ml/)). At Meta, showing AI patches to human reviewers raised time-in-review by 5.5% until the patches were hidden from reviewers ([Meta](https://arxiv.org/html/2507.13499v1)). Anthropic's managed Code Review verifies each finding before posting and reports fewer than 1% of findings marked incorrect, at about $15–25 per review. That is vendor-reported, with no independent replication ([Claude blog](https://claude.com/blog/code-review)). The right stance is to use AI review as a high-precision defect triage step, never as a source of patches to apply automatically.

**Keep each PR within human review capacity.** Human defect detection drops beyond 200–400 LOC per review and above about 500 LOC per hour ([SmartBear](https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/)). This is old vendor data, but it is consistent with Google's finding that the median change there modifies 24 lines ([Sadowski et al., ICSE-SEIP 2018](https://doi.org/10.1145/3183519.3183525)). AI adoption is pushing in the opposite direction: vendor telemetry from 1,255 teams shows **PR size up 154% and review time up 91%** on high-adoption teams ([Faros AI](https://www.faros.ai/blog/ai-productivity-paradox-report-2025)). Among 33,596 agent PRs, each changed line lowered merge odds by about 1% and each failed CI check by about 15%. Duplicate PRs made up 23% of classified rejections ([Ehsani et al.](https://arxiv.org/html/2601.15195)). Larger PRs also attract more AI findings: 84% of PRs over 1,000 lines got findings versus 31% under 50 lines ([Claude blog](https://claude.com/blog/code-review)). Claude Code's `/batch` splits a large mechanical change into 5–30 units, each with its own worktree and PR ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)), and Graphite's `gt mcp` lets Claude Code create stacked PRs ([Graphite](https://graphite.com/docs/gt-mcp)). Neither has been evaluated empirically, but both put the size evidence into practice.

**Make commits small and meaningful, and keep history recoverable.** Beck's rule is the sharpest atomicity heuristic available: "Never mix structural and behavioral changes in the same commit," and commit only when tests pass and warnings are resolved ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)). Human messages are often poor too: about 44% of commit messages in active OSS projects could be improved, mostly by stating *why* ([Tian et al.](https://arxiv.org/abs/2202.02974)), and an agent has the task context to supply it. For review fixes on an unshared branch, `git absorb --and-rebase` folds staged hunks into the commits they belong to without opening an editor, and can be undone with `git reset --soft PRE_ABSORB_HEAD` ([git-absorb](https://github.com/tummychow/git-absorb)). Squash-merge is the safe default when branch history is noisy, though no study compares merge strategies. Armin Ronacher argues for squashing on merge while keeping the full attempt history retrievable, so models stop repeating discarded paths ([Ronacher](https://lucumr.pocoo.org/2025/12/22/a-year-of-vibes/)). On the server side, GitHub rulesets can require PRs, status checks, linear history, and approval from someone other than the last pusher, which closes the loop where a bot approves its own push ([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Open-source policy has converged on disclosure plus accountability. LLVM requires an `Assisted-by:` trailer and holds that a contribution "should be worth more to the project than the time it takes to review it" ([LLVM](https://llvm.org/docs/AIToolPolicy.html)). The Linux kernel says "AI agents MUST NOT add Signed-off-by tags" ([kernel docs](https://docs.kernel.org/process/coding-assistants.html)). Claude Code's `attribution` setting controls the trailer and PR line ([settings reference](https://code.claude.com/docs/en/settings-reference)).

## The recommended method, layer by layer

The method below is the best-supported assembly of these components. It is not "perfect." No combination guarantees clean output: hooks can be bypassed through subprocess writes, LLM judges are probabilistic, gates can be gamed, and humans under load approve without reading closely. What the layers do is make each kind of slop *less likely to be created, more likely to be caught, and cheap to remove*. The guiding rule, taken from Anthropic: anything that "has to happen every time" belongs in a hook, deny rule or CI. Prose is for guidelines and for naming the sanctioned alternative ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

| Phase | Do this | Enforce with tools | Leave to prose / judgment | Evidence |
|---|---|---|---|---|
| **Set-up (once per repo)** | Short, human-written CLAUDE.md/AGENTS.md (<~100–200 lines): commands, non-obvious decisions, sanctioned locations. Grow it from observed failures. | Formatter on PostToolUse; linters and type checker; architecture contracts; jscpd new-clone baseline; dead-code tool in CI; pre-commit; protected `main` ruleset with required checks and last-pusher approval; agents off bypass lists | Conventions, "search before writing," where docs go | Moderate (controlled on context files; practitioner on harness) |
| **Before each task** | Fresh session, own worktree/branch from fresh `main`. For non-trivial work: a ≤1-page spec (what, acceptance criteria, out-of-scope, expected files) kept out of the tracked tree. Write or approve failing tests first. | `claude -w`; tests protected from edits; scratch location gitignored | Proportional planning; skip specs for small fixes | Strong for runnable done-criteria; weak for spec tooling |
| **During** | One task at a time; watch the first minute; `/clear` after two failed corrections; search for existing utilities before adding new ones | Write gate for stray artifacts; Bash gate for unsafe git; edit-time lint; capped verifier retries (≈2) | Reuse, minimal change, no speculative abstraction | Strong (tool feedback); moderate (reuse index) |
| **End of turn** | Agent shows command output as evidence, not "all tests pass" | Stop hook: untracked-clutter sweep, scope check against declared files, new clones, verifier pass | none | Strong (verification); unmeasured (clutter sweep) |
| **After implementation** | Separate minimization pass, then a fresh-context, read-only reviewer against the spec, limited to correctness, scope and reuse; fix only verified findings | Reviewer tools limited to Read/Grep/Glob; tests re-run after minimization | Whether a finding matters | Strong (minimization); moderate (fresh reviewer) |
| **Commit** | Atomic Conventional Commits that state *why*; structural vs. behavioral split; review fixes folded with `git absorb` on unshared branches | Commit-message lint; staged-clutter check; no `--no-verify`, `-A`, `-a`; no agent `Signed-off-by`; attribution trailer kept | Commit boundaries | Moderate (size/CI); weak (message format) |
| **PR** | ≤~400 changed LOC, one purpose, CI green before opening, check for duplicate PRs, human-curated description; split with `/batch` or stacks | CI as hard gate; PR-size check; optional verified AI review; human approval | Design, intent, knowledge transfer | Moderate–strong |
| **Ongoing** | Turn every repeated mistake into a rule or check; schedule cleanup | Periodic dead-code/duplication audit; telemetry on gate firings | Pruning rules that are really preferences | Anecdotal (Hashimoto, OpenAI, Cherny) |

Two constraints keep the method from becoming the over-engineering it is meant to prevent. First, **keep the enforced set small**. Anthropic warns that "if you ever find yourself at forty of them, most are probably preferences" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)), and every false positive pushes users to switch the guard off. Second, **budget the loops**. Stripe caps CI retries at two, the Stop hook has its own continuation cap, and OpenAI moved from spending 20% of every week on manual "AI slop" cleanup to recurring background cleanup agents because manual cleanup "didn't scale" ([OpenAI](https://openai.com/index/harness-engineering/)).

## Nine upgrades would close no-git-slop's biggest gaps

The current plugin covers the artifact layer the evidence leaves to tooling: a stdlib rules engine for new files, a SessionStart baseline, Write and Bash gates, a Stop sweep, CLI, pre-commit, CI template, AGENTS.md template, a gitignored `.scratch/`, and a `tidy` skill. Measured against the method above, it does not yet address scope drift, diff size, duplication, test and config tampering, or verification evidence, and it has no way to show that it works. The upgrades below are ordered by expected value per false-positive risk. Each is designed to *redirect* rather than only deny, in keeping with the earlier design principle.

| # | Upgrade | Mechanism | Why (evidence) |
|---|---|---|---|
| 1 | **Gate-firing telemetry** | Append JSONL records (rule, decision, path pattern, what Claude did next) to `${CLAUDE_PLUGIN_DATA}`; `ngs stats` summarizes; nothing leaves the machine without opt-in | We found no published measurement of stray-file or hygiene rates; a precondition for tuning and for the eval below |
| 2 | **Protect tests and guard configs** | PreToolUse `ask` on deleting or weakening test files, and on edits to `.jscpd.json`, `.importlinter`, eslint/ruff configs, `.pre-commit-config.yaml`, `.claude/settings*.json`, the plugin's own policy | Analyzer gaming by deletion ([Kadam](https://arxiv.org/pdf/2610.38977)); test-cheating ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)); "unacceptable to remove or edit tests" ([Anthropic harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) |
| 3 | **Diff-size budget** | Stop and commit gates compute `git diff --shortstat` against merge-base; above a configurable budget (default ~400 changed LOC, excluding lockfiles/generated) return `ask` with a split suggestion (`/batch`, stacked branches) | Merge odds fall ~1% per line ([Ehsani et al.](https://arxiv.org/html/2601.15195)); review effectiveness drops past 400 LOC ([SmartBear](https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/)) |
| 4 | **Declared-scope check** | Optional `.scratch/task.md` (or `ngs scope add <glob>`) lists expected paths; Stop reports changed files outside scope, once per turn, as "revert, justify, or add to scope" | Undeclared changes caught by file-inventory checks ([Gated SDD audit](https://arxiv.org/pdf/2611.05094)); Spotify's judge vetoes ~25% for scope ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)); deterministic, unlike a judge |
| 5 | **New-clone gate plus interface index** | If jscpd is installed, Stop runs `--baseline-from-ref <merge-base> --fail-on-new-clones`; a new `ngs index` prints a signatures-only list of shared utilities that the `tidy` skill tells Claude to consult before adding helpers (on demand, not injected every session) | Interface listing raised reuse to 67.8%, full source did not ([RepoReuse](https://arxiv.org/pdf/2609.35357)); duplication is invisible to tests; LLM-generated overviews hurt ([Gloaguen et al.](https://arxiv.org/html/2602.11988)) |
| 6 | **`minimize` and `review` agents** | Two plugin subagents: `slop-minimizer` (removes changes not needed for the tests/spec, then re-runs tests) and `slop-reviewer` (`tools: Read, Grep, Glob`; reviews the diff against the spec for correctness, scope and reuse; "skip style"; verifies each finding before reporting) | A separate minimization pass works ([RECAP](https://arxiv.org/html/2608.13292v1)); agentic self-minimization often fails ([TRIM](https://arxiv.org/pdf/2607.18161)); unscoped reviewers add bloat ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) |
| 7 | **Verification evidence at Stop** | Optional `verify` command in policy (e.g. `make check`); run only when tracked code changed this turn; return terse, regex-filtered errors; cap re-entries at two per task | Spotify's Stop-hook verifiers ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)); Stripe's two-round cap ([Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)); tool feedback beats introspection ([SWE-agent](https://arxiv.org/pdf/2405.15793)) |
| 8 | **Commit and PR hygiene extensions** | Bash gate: block agent-added `Signed-off-by`/`--signoff`; warn on commits mixing renames/moves with logic edits (structural vs. behavioral); recommend `git absorb` over "address review" commits on unshared branches; on `gh pr create`, check diff budget, CI status, and `gh pr list --search` for duplicates | Kernel DCO rule ([kernel docs](https://docs.kernel.org/process/coding-assistants.html)); Beck's split ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)); failed CI and duplicate PRs drive rejection ([Ehsani et al.](https://arxiv.org/html/2601.15195)) |
| 9 | **`ngs init` ecosystem wiring** | Detect language and offer (never force) a PostToolUse formatter hook, import-linter / eslint-plugin-boundaries starter contracts with remediation-style messages, knip/vulture in CI, ruleset checklist (required checks, last-pusher approval, no bot bypass) | Remediation messages in lints ([OpenAI](https://openai.com/index/harness-engineering/)); PostToolUse format ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177.html)); server-side backstop ([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)) |

A few things should deliberately *not* be added. The plugin should not inject a generated repository overview, should not bundle a heavy spec framework, and should not add an LLM judge as a blocking gate. Anthropic notes that `prompt` and `agent` hooks are not deterministic ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)), and Spotify has no evals for its judge. It also should not grow the always-on reminder past a few lines. The Stop hook's "one block per turn" behavior should apply to *all* Stop findings combined, so the new checks do not compete for continuations. Fail-open behavior should be kept for the advisory checks (scope, size, clones) and fail-closed only for the commit gate.

## Evaluating the plugin: a pre-registered, paired A/B with independent metrics

No benchmark measures repo hygiene for agents, so no-git-slop has to produce its own evidence. The design should follow the published methodology for agent evals and avoid the main trap the literature identifies: **a tool that targets a metric often improves only that metric** ([Kadam](https://arxiv.org/abs/2610.38977)).

**Tasks.** Use 40–60 tasks. About half should come from merged PRs, following Khatri's recipe: the PR description as the prompt, the pre-PR commit as the start state, and the PR's tests hidden as gold tests ([Khatri](https://www.alphaxiv.org/abs/2607.27250)). That yields a gold file set and gold diff size for scope and size metrics. Add open-ended feature, refactor and debugging tasks, because that is where summary docs, scratch scripts and copies appear. Add a small set of *provocation* tasks ("investigate why X is slow," "summarize what you changed") that tempt the agent to write reports or throwaway scripts. Include several sequential three-task episodes in the style of SWE-Maintain, since single-patch scoring misses compounding mess. SWE-Maintain found agent-produced history lowered later-task resolution by 5.6 pp, and the penalty disappeared when earlier tests still passed ([SWE-Maintain](https://arxiv.org/abs/2610.14768)).

**Arms.** Run four arms. Baseline is plain Claude Code via `claude --bare -p` with a fixed settings file. Full plugin is loaded via `--plugin-dir`. Prose-only uses the AGENTS.md template and `tidy` skill with no hooks, which isolates what the gates add over instructions. Placebo uses a context file of equal length with no hygiene content, which separates content effects from token effects. If budget allows, add a budget-matched best-of-n baseline, which Kadam found beats most "quality" techniques ([Kadam](https://arxiv.org/pdf/2610.38977)). Pin the model and CLI version. Verify that the plugin actually loaded in each treatment run from the `stream-json` `system/init` event, which lists `plugins` and `plugin_errors` ([Claude Code headless](https://code.claude.com/docs/en/headless)).

**Trials and isolation.** Run 3–5 trials per task per arm, randomized and interleaved in time. Each trial gets a fresh container or worktree, because leftover files, caches or git history cause correlated failures ([Anthropic evals](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). Harbor already runs Claude Code in containers on custom task sets ([Harbor](https://raw.githubusercontent.com/harbor-framework/harbor/HEAD/README.md)). A shell loop over `claude --bare -p ... --output-format stream-json --max-budget-usd` works as well. For each trial, capture `git status --porcelain --ignored`, untracked files, the full patch and `--stat` from base, `git log`, a worktree tarball, the transcript, and cost.

| Tier | Metric | Role |
|---|---|---|
| Primary (pre-registered) | Stray artifacts per task: new untracked or committed files matching no gold path and classified as junk (reports, scratch scripts, copies, logs) | Main hypothesis |
| Hygiene secondary | Out-of-scope files vs. gold set; diff size relative to gold; commits per task, files per commit, message conformance; agent `Signed-off-by` or bypass attempts | Plugin's direct targets |
| Independent quality | New clones (jscpd), complexity delta (lizard/Sonar), analyzer warnings per KLOC added, dead code added, LLM-judge rubric with one judge per dimension, human blind rating on a sample | Detects metric-gaming and displacement |
| Guardrails | Hidden-test pass rate (TOST equivalence, e.g. ±5–10 pp); regression preservation across episodes; cost, turns, wall time | "No harm" claims |
| Mechanism | Gate firings per task; false-positive rate from human labeling of a random sample of denials; how often Claude complied vs. routed around (e.g. Bash heredoc writes) | Explains effects, tunes rules |

**Analysis.** Use mixed-effects models with task as a random effect (logistic for binary outcomes, Poisson or negative binomial for counts), Cochran–Mantel–Haenszel for stratified binary comparisons as in Gloaguen et al. ([Gloaguen et al.](https://arxiv.org/html/2602.11988)), and paired bootstrap CIs for continuous metrics. Run a power calculation before running anything. Khatri's design (15 + 17 tasks × 3 runs × 3 strategies) could detect only effects larger than 30 pp ([Khatri](https://www.alphaxiv.org/abs/2607.27250)). Stray-file counts are probably more sensitive than pass rate, but that needs a pilot to confirm. Report pass@k and pass^k ([Anthropic evals](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)), read transcripts to confirm the rules were actually followed, and publish null results. A credible success claim would look like this: the full-plugin arm cuts stray artifacts and out-of-scope files compared with *both* baseline and prose-only; independent quality metrics do not get worse; pass rate stays within the equivalence margin; and cost overhead is reported. After launch, opt-in field telemetry (upgrade 1) and a revert/rework signal on merged agent PRs, such as agent-introduced code deleted within days (a median of 3 days for agents vs. 34 for humans in earlier work ([Pham & Ghaleb](https://arxiv.org/abs/2601.17627))), can show whether lab effects carry over to real repositories.

## Conclusion

The research shifts the target. "Clean output" is not mainly a property of the prompt or even of the agent. It is a property of the loop around the agent: what it can run, what it is stopped from doing, who reviews it with fresh eyes, and how small the unit of work is. The most useful insight from the controlled work is that generation and cleanup are different jobs. Agents asked to be minimal while solving a problem are not minimal. Agents whose output is minimized and reviewed afterward, against tests and a spec, are much closer. That points no-git-slop beyond its current role as a filesystem bouncer. It can also orchestrate the post-task pass (minimize, scoped review, size and scope budgets) while keeping its deterministic core small.

The honest limit is that every layer leaks. Subprocess writes get past Write gates, judges misfire, gates get gamed, and tired humans approve large diffs. The method lowers the rate of slop and the cost of removing it; it does not bring either to zero. The field still lacks the one measurement that would settle the question: a benchmark of repo hygiene across sequential agent tasks. A well-run evaluation of no-git-slop, with a prose-only arm, independent quality metrics and published false-positive rates, would be among the first such datasets. That makes the evaluation as valuable as the plugin itself.
