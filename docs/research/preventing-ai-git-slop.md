# Gate the filesystem, not the prompt

Prose instructions alone will not keep Claude Code from producing git slop. A small set of deterministic gates will, as long as each gate redirects Claude to a sanctioned alternative instead of only forbidding things. The evidence lines up on this. Controlled studies find that agents obey context files closely but that those files do not improve correctness. Instruction-following degrades as rule counts and context length grow. Anthropic's own documentation says CLAUDE.md is "context, not enforced configuration" and that rules which must always hold belong in hooks or deny rules. Meanwhile, large observational datasets show AI-era code duplicating more and refactoring less. Users also report Claude models ignoring always-on "don't create .md files" rules. The existing ecosystem is split. Rule packs are hugely popular but only advisory, hook collections focus on safety rather than hygiene, and "slop linters" inspect code content but not repo structure. None of them gates *file creation and repo layout*. no-git-slop should fill that gap as a single-repo Claude Code plugin and marketplace. Its core is one dependency-light policy engine called from four hooks: SessionStart baseline, PreToolUse on Write, PreToolUse on git, and a Stop sweep. The same engine is reused by pre-commit and CI. It should ship with a short skill, a read-only reviewer subagent, a scratch directory outside the repo, and optional wiring to proven tools (jscpd, gitleaks, commitlint, ls-lint).

## Measured AI code quality: more duplication, less refactoring, faster deletion

The quality signals are strongly correlated with AI adoption, though none of them proves causation. GitClear's 2026 "Write-Only Mode" report covers 623M changes. It found duplicated blocks rising from **40.3 to 73.0 per million changed lines (+81% vs. 2023)**. Moved code, its refactoring proxy, fell **from 21% of changed lines in 2022 to 3.8%**, and copy/paste rose from 9.4% to 15.7% ([GitClear](https://www.gitclear.com/write_only_mode_ai_research)). The same report found function connectivity down 35%, within-commit copy/paste up 41% and error-masking constructs up 47% ([GitClear](https://www.gitclear.com/write_only_mode_ai_research)). GitClear sells code analytics, does not say how it identified AI-authored code, and reports no statistical tests. It also says its finding is "not 'AI writes bad code'." So these are trend lines that coincide with AI adoption, not measured effects of AI. GitClear's 2025 report showed the same direction a year earlier: duplicated 5+ line blocks rose 8x during 2024, and copy/paste overtook moved lines for the first time ([DevClass](https://www.devclass.com/ai-ml/2025/02/20/ai-is-eroding-code-quality-states-new-in-depth-report/1626250)).

PR-level studies point the same way. CodeRabbit, which also sells review tooling, audited 470 OSS PRs and found **10.83 vs. 6.45 issues per PR (about 1.7x)** for AI-co-authored PRs. Readability issues were more than 3x higher and excessive I/O about 8x higher ([CodeRabbit](https://www.coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report)). The AIDev dataset of 456,535 agent PRs puts Claude Code's merge rate in popular repos at **52.5% vs. 76.8% for humans**. On documentation PRs, though, Claude Code merges more often than humans, 85.7% vs. 76.5% ([arXiv 2507.15003](https://arxiv.org/html/2507.15003v1)). Ehsani et al. looked at 33k agent PRs and found that unmerged ones are larger, touch more files, fail CI more often, and are rejected for duplicate PRs and unwanted features ([arXiv 2601.15195](https://arxiv.org/abs/2601.15195)). The best quantitative proxy for throwaway code comes from Pham and Ghaleb: functions and classes that agents introduce are deleted after a **median of 3 days, versus 34 days** for human ones ([arXiv 2601.17627](https://arxiv.org/abs/2601.17627)). They also found that agent PR descriptions align less well with the commits they summarize. Commit-message length was the strongest predictor of PR description quality, which suggests agents stitch PR descriptions together commit by commit ([arXiv 2601.17627](https://arxiv.org/abs/2601.17627)).

The specific behavior no-git-slop targets, stray files, has a clear anecdotal record but no direct measurement. Cursor forum users report Claude models writing unrequested Markdown documents hundreds of lines long. In one case, nine new `.md` files appeared over five prompts even though an `alwaysApply: true` rule forbade them ([Cursor forum](https://forum.cursor.com/t/claude-models-with-cursor-constantly-wastefully-generate-md-docs-files-violating-rules/147673)). Another user says Sonnet 4.5 "keeps creating useless .md, .sh, .txt or test files" ([Cursor forum](https://forum.cursor.com/t/claude-sonnet-4-5-keeps-creating-useless-md-sh-txt-or-test-files-without-actually-executing-the-fixes/138681)). In Claude Code itself, issue #1342 documents copies of a Swift file under `ErrorFixes/NuclearFix/` and `ErrorFixes/DataExplorerBackup/` that broke the Xcode build. Anthropic closed it as "likely much better with the most recent models" ([GitHub](https://github.com/anthropics/claude-code/issues/1342)). I found no peer-reviewed or preprint study that counts stray summary files, scratch scripts or WIP commits per agent session. no-git-slop should therefore present itself as evidence-*aligned* rather than evidence-*proven*. It could help close the gap by logging how often each gate fires, which would give the project its own measurements.

## Context files steer behavior reliably but do not buy correctness

The best controlled study is Gloaguen et al. (an ICLR 2026 workshop paper). It found that a repository context file "does not generally improve" task success while "increasing inference cost" by over 20% on average across Claude Code, Codex and Qwen Code ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). LLM-generated files had no significant effect on task success (-0.5% on SWE-bench Lite, -2% on CTXbench). Developer-written files scored about 7 points higher than LLM-generated ones, a significant difference (p=0.038). Developer files helped every agent except Claude Code ([arXiv HTML v3](https://arxiv.org/html/2602.11988v3)). The finding that matters for no-git-slop is that **agents follow instructions closely**. When a file mentioned `uv`, the agent used it **1.6 times per instance, versus under 0.01** when the file didn't mention it. Repo-specific tools went from under 0.05 uses to 2.5 ([arXiv HTML v3](https://arxiv.org/html/2602.11988v3)). That compliance is also what drives the cost. Removing the testing section cut cost significantly ($0.4715 → $0.3730 on CTXbench) with no significant loss of accuracy ([arXiv HTML v3](https://arxiv.org/html/2602.11988v3)). Repository overviews, which vendors recommend, did not help agents navigate, and LLM-generated files mostly repeated existing docs ([arXiv HTML v3](https://arxiv.org/html/2602.11988v3)). Khatri's two-agent ablation (288 runs) supports the correctness result: context strategy had no measurable effect, and agents failed mainly on implementation skill, not on missing repository knowledge ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)). Lulla et al. is the dissenting study. It found AGENTS.md cut median runtime by 28.64% and output tokens by 16.58% ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404)). The likely reason is that it measured different things (runtime and output tokens rather than total cost and steps) on different tasks.

Research on instruction density points toward fewer rules. IFScale tested 20 models and found the best frontier models reach only **68% accuracy at 500 simultaneous instructions**, with a bias toward instructions that appear early ([arXiv 2507.11538](https://arxiv.org/abs/2507.11538)). Chroma's "Context Rot" study of 18 LLMs found that performance fell with input length in every experiment, even a trivial one. A single distractor lowered accuracy ([Chroma](https://www.trychroma.com/research/context-rot)). Gloaguen found no clear relationship between file length and success over 24–2,003 words, so the risk is less about word count and more about the number of competing rules and about irrelevant or unwanted rules that still get obeyed. Anthropic's guidance agrees. CLAUDE.md files should stay **under 200 lines**, because "Longer files consume more context and reduce adherence" ([Memory docs](https://code.claude.com/docs/en/memory)). Adding IMPORTANT or ALL CAPS "mostly makes Claude over-apply the rule." And "If something has to happen every time, make it a hook, a deny rule, or a managed setting" ([Best practices](https://code.claude.com/docs/en/best-practices)).

Taken together, this defines what no-git-slop's prose layer should be. It should be short, human-written and limited to conventions. It should never auto-generate an overview, and it should be loaded on demand through a skill rather than always on. The most important rules go first. Correctness and hygiene must not depend on it. Because compliance is high, prose works well for naming the *sanctioned alternative*, such as "put scratch notes in the scratch directory" or "run `ngs check` before committing." It works poorly as a prohibition the model must remember forty turns later.

## Claude Code offers four guaranteed levers, and each has a sharp edge

Anthropic's docs divide instructions into two kinds. Prompts, CLAUDE.md and skills come with no guarantee. Hooks, deny rules and managed settings are applied "every time" ([Best practices](https://code.claude.com/docs/en/best-practices)). no-git-slop needs to know several details of the enforcement side.

**PreToolUse is the only point where a write can be stopped before it happens.** A `command` hook receives JSON on stdin. A `Write` call carries `tool_input.file_path`, which is always absolute and uses backslashes on Windows, along with the full `content`. The hook can return `hookSpecificOutput.permissionDecision: "deny"` with a reason, or exit 2 so that stderr goes back to Claude ([Hooks reference](https://code.claude.com/docs/en/hooks)). A hook that exits 2 "stops the tool call before permission rules are evaluated", so it holds even when an allow rule would otherwise let the write through ([Permissions](https://code.claude.com/docs/en/permissions)). PostToolUse runs after the tool and cannot undo the write. It can only feed back to Claude. Its `tool_response.type: "create"` does confirm that a new file was created ([Hooks reference](https://code.claude.com/docs/en/hooks)). The Write input does not say whether the target already exists, so the hook has to check the filesystem itself.

**Permission rules cannot express "no new Markdown files."** The docs are explicit that for a path rule on `Write`, Claude Code "accepts a rule… but doesn't match" it. A rule like `Edit(**/*.md)` would block *every* Markdown edit, including edits to README.md ([Permissions](https://code.claude.com/docs/en/permissions)). Bash rules match command text and are easy to get around. `Bash(git push *)` does not stop `git -C . push origin main`, and the docs say such a rule "isn't a security boundary." Read/Edit denies also do not reach "arbitrary subprocesses that read or write files indirectly, like a Python or Node script" ([Permissions](https://code.claude.com/docs/en/permissions)). So `cat > foo.py <<EOF` or `python -c "open('x.py','w')"` will get past any Write gate. That gap is why an end-of-turn `git status` sweep is a required backstop, not an optional extra.

**Stop hooks can send Claude back to clean up, and they have built-in loop protection.** If a Stop hook exits 2 or returns `decision: "block"`, the turn continues and the reason becomes Claude's next instruction. Anthropic's canonical example is `pnpm tsc --noEmit 1>&2 || exit 2` ([Best practices](https://code.claude.com/docs/en/best-practices)). Input includes `stop_hook_active` and `last_assistant_message`, and the docs advise reading `last_assistant_message` instead of the transcript. After **8 consecutive continuations** Claude Code overrides the block, and the count resets whenever Claude calls a tool. The cap can be changed with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` ([Hooks reference](https://code.claude.com/docs/en/hooks)). The docs also say `prompt` and `agent` hooks ask "another model" and are not deterministic. Real enforcement should use `command` hooks with `onFailure: "block"` ([Best practices](https://code.claude.com/docs/en/best-practices)).

**Plugins are the distribution unit, with some limits.** A plugin consists of `.claude-plugin/plugin.json`, where only `name` is required, plus `skills/`, `agents/`, `hooks/hooks.json` (the file must have a top-level `"hooks"` wrapper), `bin/` (added to the Bash tool's PATH) and `settings.json`. A CLAUDE.md at the plugin root "isn't loaded as context." State belongs in `${CLAUDE_PLUGIN_DATA}`, not in `${CLAUDE_PLUGIN_ROOT}`, because the root path changes on update ([Plugin reference](https://code.claude.com/docs/en/plugins-reference)). Plugin subagents ignore `hooks` frontmatter, so all hooks have to live in `hooks/hooks.json` ([Subagents](https://code.claude.com/docs/en/sub-agents)). A plugin's `settings.json` only applies the `agent` and `subagentStatusLine` keys. Keys such as `includeGitInstructions` (which turns off Claude's built-in commit/PR instructions and git status snapshot) or `attribution` therefore have to be set in user or project settings ([Settings reference](https://code.claude.com/docs/en/settings-reference)). Interactive sessions hold back hooks until the user accepts workspace trust. `-p`/SDK runs treat the folder as trusted ([Hooks reference](https://code.claude.com/docs/en/hooks)). Plan files already default to `~/.claude/plans`, outside the repo ([Settings reference](https://code.claude.com/docs/en/settings-reference)), which shows a sanctioned scratch location working.

Anthropic adds a constraint that should shape the whole design: "keep the enforced set small… If you ever find yourself at forty of them, most are probably preferences" ([Best practices](https://code.claude.com/docs/en/best-practices)). Every false positive teaches users to disable the plugin.

Two of these matter most for an agent. First, jscpd's baseline mode ignores existing duplication and fails only on *new* clones. That fits the GitClear duplication signal directly and does not punish legacy code. Second, a Claude Code PreToolUse hook on `git commit` catches what local git hooks cannot, such as `--no-verify`. CI is still needed, because commitlint's own docs warn that local hooks can be bypassed ([commitlint](https://commitlint.js.org/guides/local-setup.html)). Commit atomicity has no mechanical linter. The best available proxies are the Conventional Commits FAQ advice to split a change that fits more than one type ([spec](https://www.conventionalcommits.org/en/v1.0.0/)), a limit on files per commit, and a check that flags mixed `docs/` + `src/` commits.

## Prior art stops at advice or safety and leaves hygiene ungated

Rules-only packs are by far the most popular approach. andrej-karpathy-skills (now multica-ai/andrej-karpathy-skills) had about 232k stars as of a page snapshot. It encodes "Simplicity First" and "Surgical Changes" (edit only what was asked, and mention unrelated dead code rather than deleting it), but no hooks are visible ([GitHub](https://github.com/multica-ai/andrej-karpathy-skills)). obra/superpowers (about 321k stars) injects a bootstrap through a SessionStart hook. It ships skills for TDD, plans, git worktrees and finishing a branch, but nothing on file-creation discipline is visible ([GitHub](https://github.com/obra/superpowers)). Both star counts come from web pages and could not be checked against the API. The Cursor reports above show what happens to always-on rules: models ignore them.

Hook collections enforce safety, not hygiene. karanb192/claude-code-hooks guards secrets, dangerous commands and git safety, protects tests from deletion, and has a config-guard that stops the agent editing its own hooks. Tiered `HOOK_SAFETY_LEVEL` settings switch hooks between deny and ask ([GitHub](https://github.com/karanb192/claude-code-hooks)). disler/claude-code-hooks-mastery gates Python writes with Ruff and ty validators ([GitHub](https://github.com/disler/claude-code-hooks-mastery)). nizos/tdd-guard uses model judgment to block over-implementation, and has since grown into "Probity" ([GitHub](https://github.com/nizos/tdd-guard)). bcanfield's debt-ops logs agent shortcuts to the repo instead of hiding them ([GitHub](https://github.com/bcanfield/agentic-tech-debt)). Content-level slop linters such as KarpeSlop score TS/JS for redundant comments, hallucinated imports and hedging. They exit 2 in CI but do not look at file layout, and KarpeSlop does not support Python ([KarpeSlop](https://cdn.jsdelivr.net/npm/karpeslop@1.0.30/README.md)). The most useful idea comes from a small tool called mkmd. It wraps `mktemp` to send agent plans and notes to `$XDG_STATE_HOME/mkmd/<project>/<date-branch>/`, outside the repo, so `git status` stays clean without any `.gitignore` edits ([i9wa4 blog](https://i9wa4.github.io/en/blog/2026-03-22-mkmd-mktemp-wrapper-for-ai-agents.html)). Giving the agent a place where scratch work belongs works better than only forbidding scratch files, and it matches the compliance finding in Gloaguen et al.

None of the surveyed tools has a **new-file guard** (forbidden filename patterns, a root-level allowlist, detection of `_v2`/`_fixed`/`Backup` copies). None ties a write-time gate, an end-of-turn sweep and CI to **one shared policy**. That combination is no-git-slop's niche.

The policy itself should encode existing conventions rather than invent its own. GitHub looks for community health files in `.github/`, then the root, then `docs/` ([GitHub Docs](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)). Keep a Changelog 1.1.0 uses an Unreleased section and Added/Changed/Deprecated/Removed/Fixed/Security, and warns against dumping commit logs into the changelog ([keepachangelog.com](https://keepachangelog.com/en/1.1.0/)). PyPA explains the trade-offs of the src layout ([PyPA](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)). Go's official layout uses `internal/` and `cmd/` and does not mention `pkg/` ([go.dev](https://go.dev/doc/modules/layout)), so golang-standards' `pkg/` should not be treated as a standard. Diátaxis sorts docs into tutorials, how-to guides, reference and explanation ([diataxis.fr](https://diataxis.fr/)), which gives a principled answer to "where does this new doc go?" in place of `IMPLEMENTATION_NOTES.md` at the root. AGENTS.md is the cross-tool instruction file, stewarded under the Linux Foundation, and the nearest nested file wins ([agents.md](https://agents.md/)).

## Recommended design for no-git-slop

The architecture rests on four principles drawn from the evidence above. There should be **one policy engine with three entry points**: Claude Code hooks, pre-commit, and CI. Each block should **redirect rather than only deny**, so every denial reason names the correct location or command. The **enforced set should stay at about ten checks**, per Anthropic's warning. Prose should be **short, loaded on demand and focused on sanctioned alternatives**. The engine should be a single Python 3 standard-library script, matching the language of Anthropic's own hook example ([example](https://raw.githubusercontent.com/anthropics/claude-code/main/examples/hooks/bash_command_validator_example.py)), so it installs with no dependencies. Heavier tools run only if they are installed.

### Repository layout

The repo is its own marketplace (the marketplace.json `source` is a relative path, with no `..`) and keeps its own house clean, which is the best demonstration of the plugin.

### The four hooks

```json
{"hooks": {
  "SessionStart": [{"matcher": "startup|resume|clear|compact",
    "hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/bin/ngs hook session-start"}]}],
  "PreToolUse": [
    {"matcher": "Write",
     "hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/bin/ngs hook pre-write"}]},
    {"matcher": "Bash",
     "hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/bin/ngs hook pre-bash", "onFailure": "block"}]}],
  "Stop": [{"hooks": [{"type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/bin/ngs hook stop"}]}]
}}
```

**SessionStart** saves a baseline of `git status --porcelain --untracked-files=all` to `${CLAUDE_PLUGIN_DATA}/<session_id>.json`. Later checks then flag only files Claude created and leave the user's existing untracked files alone. It also returns about eight lines of `additionalContext` naming the scratch command and the commit skill. Because it matches `compact`, that context is re-injected after compaction, which addresses the context-rot problem without an always-on CLAUDE.md.

**PreToolUse Write** normalizes the path and returns immediately if the file already exists, since edits to existing files are not slop. For new files it checks, in order: forbidden patterns (`*SUMMARY*.md`, `*_NOTES.md`, `*_v2.*`, `*_new.*`, `*_fixed.*`, `*.backup`, `*.orig`, `tmp_*`, root-level `test_*.py`/`*.sh`); a root allowlist built from the GitHub health-file and language-manifest conventions; Markdown outside `docs/` or the known meta files; and a **same-basename-elsewhere** check, which catches the `ErrorFixes/NuclearFix/` copy pattern from issue #1342. A denial reason always gives the alternative, for example "write scratch notes to `$(ngs-scratch)`" or "edit `src/foo.py` in place instead of creating `foo_fixed.py`" or "user-facing docs go in `docs/how-to/`." The `mode` userConfig switches between `deny`, `ask` and warn-only, borrowing karanb192's tiers. The Write gate should fail *open*, because a crashed gate should not brick a session. The Stop sweep and CI catch whatever it misses.

**PreToolUse Bash** matches every Bash call instead of relying on `if: "Bash(git *)"`. The docs call `if` best-effort and Bash patterns bypassable, so the engine tokenizes the command itself and exits within milliseconds for anything that isn't git. On `git commit` it does five things: it rejects `--no-verify`; it checks a `-m` message against Conventional Commits with a 72-character header; it runs the new-file policy over `git diff --cached --name-only --diff-filter=A`; it enforces a file-count budget (default 15) and flags mixed doc-and-code commits as `ask`; and it runs `gitleaks` on staged changes if gitleaks is installed. On `git add -A` / `git add .` it warns when the sweep would find junk. This hook fails *closed* (`onFailure: "block"`), because a bad commit is expensive to undo.

**Stop** finds new untracked or staged files relative to the baseline, filters them through the policy, and runs `jscpd --baseline-from-ref <merge-base> --fail-on-new-clones` if jscpd is installed. If anything is found, it exits 2 with a list of files and three choices for each: delete it, move it, or justify keeping it. To avoid wasting continuations, it hashes the findings and exits 0 when `stop_hook_active` is true and the hash hasn't changed. It also skips when `background_tasks` shows work still running. The 8-continuation cap is the last safeguard. Dead-code tools (knip, vulture, deadcode) are too slow and noisy for every turn. They belong in the `slop-reviewer` subagent and in CI.

### Prose, settings and install

The `clean-repo` skill stays under about 60 lines and puts its most important rules first, because of primacy bias. Search for an existing function before writing a new one, which targets the duplication signal. Make surgical changes only. Never write summary or report files; report in chat instead. Put scratch work in `ngs-scratch`. Put docs in their Diátaxis folder. Its `description` field is what stays in context until the skill is invoked. `templates/AGENTS.md` holds the same five rules for Codex, Cursor and other agents, so the Cursor-forum failure mode is covered at least advisorily. CLAUDE.md can import it with `@AGENTS.md`. Following Gloaguen et al., the plugin should never generate a repo overview.

Users install it with `/plugin marketplace add <owner>/no-git-slop` followed by `/plugin install no-git-slop@no-git-slop` ([Marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)). Teams commit `extraKnownMarketplaces` and `enabledPlugins` to `.claude/settings.json`. Each developer still has to install the plugin, and it takes effect only after workspace trust ([Settings reference](https://code.claude.com/docs/en/settings-reference)). `ngs init` copies the templates, but only those the user picks. It suggests two or three Edit deny rules (for example `Edit(**/*.orig)`), since deny rules hold even in `bypassPermissions` mode. It does not change `includeGitInstructions` or `attribution`, because those are the user's decisions and a plugin cannot set them anyway. The CI template runs `ngs check --ci` over the PR diff, a commitlint range check, jscpd in baseline mode and TruffleHog. That means humans and non-Claude agents meet the same policy. The project's own CI should replay the recorded hook-stdin fixtures against every supported event, run `claude plugin validate --strict`, and run `ngs check` on the repo itself.

## Conclusion

The research changes the question no-git-slop has to answer. The question is no longer how to phrase a rule so Claude obeys it. Agents already obey context files at rates above 100x baseline when the file names a concrete tool. The real question is how to make the clean path the easiest path at the moment a file is created, a commit is made, or a turn ends. Context files work well for pointing to sanctioned alternatives and poorly as prohibitions that must survive a long session. Hooks are the reverse. The design should therefore pair every deterministic block with a named destination, keep the enforced set small enough that users never feel the need to switch it off, and re-check at Stop and in CI. Bash and subprocess writes will always find gaps in a write-time gate.

The biggest open risk is not technical. It is that nobody has measured stray files, scratch scripts or commit hygiene in agent sessions. no-git-slop can help close that gap by logging, with the user's consent, which gate fired and what Claude did next. That would turn anecdotes like "nine `.md` files in five prompts" into the first real dataset on agent repo hygiene, and it would show which of the ten checks justify their false-positive cost.
