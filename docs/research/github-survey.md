# Combine intent, filesystem truth and git gates

Nobody has shipped the combination no-git-slop is aiming for, but every individual piece of it now exists somewhere on GitHub, and the closest competitor has already built the file half. **nyla111/sprawl-guard** (created 2026-10-14) blocks versioned copies, backups, report files and one-off scripts with per-rule deny/confirm/ask/warn modes, a near-duplicate check, a per-session file budget and, most importantly, an **intent escape hatch** that downgrades a block when the user named the file or asked for "a separate file" ([sprawl-guard README](https://raw.githubusercontent.com/nyla111/sprawl-guard/HEAD/README.md)). The git half is spread across other tools. pchalasani/claude-code-tools blocks every bulk-staging pathspec variant, janoppix/silent-code checks commit messages before and after the commit and gates `git push`, and dcg and claude-code-safety-net show how to parse commands through wrappers and heredocs ([pchalasani safety hooks](https://pchalasani.github.io/claude-code-tools/plugins-detail/safety-hooks); [silent-code](https://raw.githubusercontent.com/janoppix/silent-code/HEAD/README.md); [dcg](https://raw.githubusercontent.com/Dicklesworthstone/destructive_command_guard/main/README.md)). So no-git-slop is unique in its combination, not in any single rule: one Python stdlib engine that gates new files, bulk staging, commit messages and an end-of-turn sweep against a session baseline, and that runs the same policy in pre-commit and CI. Its v0.1.0 design has six weaknesses the survey makes urgent. It has no way to honor an explicit user request. A Write-only gate is bypassed by `cat > SUMMARY.md <<EOF` or `cp a.py a_backup.py`. The agent can edit `.no-git-slop.json` to allow itself. It can misread Claude Code's own sandbox stubs and temp files as agent slop. It would flag the plan folders that popular frameworks create by design. And it overlaps with Anthropic's own hard-coded subagent report-file block, which drew user backlash for having no opt-out ([#44657](https://github.com/anthropics/claude-code/issues/44657); [#101519](https://github.com/anthropics/claude-code/issues/101519)). The best technique combines three things. It asks what the user wanted (UserPromptSubmit), checks what is actually on disk (a baseline plus `git status`), and gates every route to disk and to git history, with a redirect in every block message, a guard that protects its own config, and the same engine backstopping at pre-commit, pre-push and CI. The earlier research adds a post-task minimize-and-review pass on top. The roadmap below puts fixing trust and bypass problems ahead of adding rules.

## The ecosystem splits into seven camps, and none covers repo hygiene end to end

The survey covered seven areas: Claude Code and cross-agent hook collections, rules and skills packs, deterministic code-slop linters, git/commit/PR and maintainer tools, workflow frameworks, code-quality tools with agent integrations, and a long tail of repos under 250 stars, most created in the last three to four months. The pattern is consistent. **Rule packs are huge but advisory**, **hook collections enforce safety rather than hygiene**, **slop linters inspect code content but not repo layout**, and **maintainer tools defend the receiving end of a PR rather than the authoring session**. The table below lists the repos most relevant to no-git-slop. Star counts have mixed provenance. Some come from a GitHub search-API snapshot on 2026-11-24, some from fetched repo pages or third-party lists, and many are unverified because the GitHub REST repos endpoint was blocked. Several very large counts on very young repos look inflated and are flagged.

Three things stand out from the catalogue. First, **"turn CLAUDE.md rules into hooks because rules fade" is now the stock pitch**. sprawl-guard, agents-scaffold and ThammanaSrinivas/guardrails all lead with it, so being deterministic no longer sets no-git-slop apart ([sprawl-guard](https://raw.githubusercontent.com/nyla111/sprawl-guard/HEAD/README.md); [agents-scaffold](https://raw.githubusercontent.com/LeeYudok/agents-scaffold/HEAD/README.md); [guardrails](https://raw.githubusercontent.com/ThammanaSrinivas/guardrails/HEAD/README.md)). Second, the content-slop linters agree on a shared canon (narrating comments, hedging, stubs, swallowed exceptions, hallucinated imports, debug prints) that no-git-slop does not need to rebuild. aislop alone covers it deterministically across 12 languages ([aislop](https://github.com/scanaislop/aislop)). Third, **the frameworks that claim the most discipline create the most tracked markdown**. Superpowers commits dated designs and plans under `docs/superpowers/`, Spec Kit leaves a `specs/NNN-*` folder per feature, and compound-engineering defaults to `docs/plans` and `docs/solutions` ([Superpowers writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md); [spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md); [compound-engineering](https://github.com/EveryInc/compound-engineering-plugin)). A hygiene tool that flags them blindly will be uninstalled by exactly the power users most likely to adopt it.

## Users and Anthropic both validate the target, and the backlash defines the guardrails

The complaints in anthropics/claude-code line up almost one for one with no-git-slop's rule set. After a security fix, one user reported Claude "created 4 documentation files totaling 1,489 lines without being asked" ([#20109](https://github.com/anthropics/claude-code/issues/20109)). A user's CLAUDE.md naming standard bans `_fix`, `_v2`, `_optimized`, `_new`, `_old`, `_temp`, `_backup`, `_copy`, `_draft`, `_updated`, `_refactored` and date suffixes, with test suffixes such as `_unit_test.py` exempt. That is a ready-made denylist ([#11569](https://github.com/anthropics/claude-code/issues/11569)). The verbose-comments issue has **259 reactions** and says "a clear, mandatory rule in CLAUDE.md does not reliably suppress it" ([#65961](https://github.com/anthropics/claude-code/issues/65961)). Cursor users report the same with Claude models: always-apply "no .md" rules ignored, and nine new `.md` files in five prompts ([Cursor forum](https://forum.cursor.com/t/claude-models-with-cursor-constantly-wastefully-generate-md-docs-files-violating-rules/147673)). claude-organizer's README shows the end state: `test-api-v1.md`, `test-api-final.md`, `test-api-final-FIXED.md`, `debug-webhook.mjs`, "87 more files at root!" ([claude-organizer](https://github.com/ramakay/claude-organizer)).

The strongest validation is that **Anthropic shipped a hard-coded version of one of no-git-slop's rules**. Since about v2.1.91, subagents get a fixed note that says "Do NOT Write report/summary/findings/analysis .md files", and their Write tool rejects such names with "Subagents should return findings as text, not write report files" ([#44657](https://github.com/anthropics/claude-code/issues/44657); [#101519](https://github.com/anthropics/claude-code/issues/101519)). The reaction matters as much as the rule. #44657 has 33 reactions and complains there is "no setting in settings.json, no environment variable, no CLAUDE.md directive" to opt out. #101519 says the block has no changelog entry and the one mechanism that removes it is undocumented and refused from project settings. The lesson for no-git-slop is direct: **an anti-report rule without an explicit-request override and a documented opt-out generates as much frustration as the slop it prevents**. This very research task is the counterexample the rule must handle. The user explicitly asked for a report saved to a named `.md` path under `reports/`, and a naive status-report rule would block exactly that.

The issue tracker also shows that **some stray files come from the harness, not the model**. In January 2026 a cluster of issues reported `tmpclaude-*-cwd` files in the working directory: #17600 alone had 72 comments and 88 reactions, and #18008 reported them "created in project root instead of system temp directory" ([#17600](https://github.com/anthropics/claude-code/issues/17600); [#18008](https://github.com/anthropics/claude-code/issues/18008)). Another report described "17+ empty files (.env, .npmrc, package.json, node_modules)" appearing in the working directory ([#46165](https://github.com/anthropics/claude-code/issues/46165)). Most important for no-git-slop's Bash gate, with the sandbox on, "`git add .` fails outright… aborts with exit 128 and stages nothing", and `git status` shows "~19 phantom untracked files that the model has no way to identify as sandbox artifacts" ([#78419](https://github.com/anthropics/claude-code/issues/78419); related [#84662](https://github.com/anthropics/claude-code/issues/84662)). A Stop sweep that blames Claude for these files, or tells it to delete device stubs, would be wrong and would waste continuations. Attribution is the other contested area. Users ask for `Assisted-by` instead of `Co-authored-by` ([#36105](https://github.com/anthropics/claude-code/issues/36105), 63 reactions), and also report trailers still appearing "Despite `includeCoAuthoredBy: false`" ([#4287](https://github.com/anthropics/claude-code/issues/4287)). Meanwhile block/aittributor adds AI attribution on purpose, and LLVM requires an `Assisted-by:` trailer ([aittributor](https://github.com/block/aittributor); [LLVM](https://llvm.org/docs/AIToolPolicy.html)). no-git-slop should expose attribution as a policy choice, never a hard-coded stance.

**sprawl-guard is the real competitor, and it is ahead on judgment.** Its rule table has thirteen rules with per-rule modes and profiles (relaxed/default/strict/off). It also has two ideas no-git-slop lacks entirely: a content-similarity rule that denies a new file 60%+ identical to an existing one, and the intent downgrade ([sprawl-guard](https://raw.githubusercontent.com/nyla111/sprawl-guard/HEAD/README.md)). The similarity rule catches copies that no suffix pattern sees, such as `handlers_clean.py` or a `NuclearFix/` copy with a new name. Where sprawl-guard is silent is the git layer: no documented staging, commit-message, push or CI enforcement. It is also very new and has no issue traffic, so its false-positive behavior is unknown. **pchalasani is ahead on staging**. Its bulk-add matcher handles `:/`, `:(top)` and `*`, and still catches them behind `env -C` and `GIT_DIR=` prefixes. It sends `--pathspec-from-file` to ask rather than deny, and its override is typed by the user as a prompt (`>allow-git`), which the agent cannot fake through a tool call ([pchalasani](https://pchalasani.github.io/claude-code-tools/plugins-detail/safety-hooks)). **silent-code is ahead on commit integrity**. It parses `-m`, `-am`, `-F` and heredoc messages before the commit, re-checks the resulting message after, gates `git push` on any unpushed violating commit, and checks `gh pr create|edit` bodies ([silent-code](https://raw.githubusercontent.com/janoppix/silent-code/HEAD/README.md)). **conclaude and karanb192 are ahead on self-defense**. conclaude protects its own config files by default, and karanb192's `config-guard` treats edits to settings, `.claude/hooks/`, `hooks.json`, `.mcp.json` and plugin manifests, and even the *creation* of a protected file, as mutations to block ([conclaude](https://connerohnesorge.github.io/conclaude/reference/config/pre-tool-use); [karanb192](https://raw.githubusercontent.com/karanb192/claude-code-hooks/HEAD/README.md)). **dcg and safety-net are ahead on parsing and portability**. dcg scans heredocs and inline scripts in three tiers (trigger, extract, AST), offers allow-once codes and an `explain` subcommand, and runs behind adapters for Claude Code, Codex, Gemini, Cursor, OpenCode and Copilot CLI. safety-net strips wrappers recursively up to five levels, and its custom rules "are additive and cannot weaken built-in protections" ([dcg](https://raw.githubusercontent.com/Dicklesworthstone/destructive_command_guard/main/README.md); [safety-net](https://konfuzian.github.io/claude-code-meta/docs/ecosystem/safety-tools)).

**hookify is the substitution risk.** Anthropic's official plugin already lets a user write `event: file` rules with a `file_path` regex and `action: block`, and its `/hookify` command can mine the recent conversation for rules to propose ([hookify](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/hookify/README.md)). A motivated user could hand-write half of no-git-slop's patterns in an afternoon. What hookify cannot express is state: "allow this because the user asked for it", "flag only files created since session start", "this `_v2` is slop because a sibling exists", "block this commit because the *staged set* contains clutter". no-git-slop's defensible value is that stateful, git-aware judgment, plus curated defaults and tests. **aislop and peakoss/anti-slop are complements, not competitors.** aislop owns code-content slop with per-edit hooks and SARIF, and no-git-slop should call it if installed rather than copy it ([aislop](https://github.com/scanaislop/aislop)). peakoss is what the PR will meet on the maintainer side: defaults derived from about 120 slop PRs a month at Coolify, a `max-failures` threshold of 4, emoji ≤2, description ≤2,500 chars, ≤5 code references, blocked doc paths, required final newline ([peakoss](https://github.com/peakoss/anti-slop)). no-git-slop can run those same checks on the authoring side before `gh pr create`.

## Six fixes come before any new rule

Each problem below is either documented in an open issue or demonstrated by a competitor's design. Each one would make users distrust the guard or let the agent route around it.

**Honor explicit user requests.** The v0.1.0 engine knows only static allow globs, so "save the report to `reports/x.md`" gets the same verdict as an unprompted `IMPLEMENTATION_SUMMARY.md`. Claude Code's UserPromptSubmit hook receives the full `prompt` text, and common hook fields can include `agent_id` and `agent_type` ([Hooks reference](https://code.claude.com/docs/en/hooks)). That is enough to record, per session, the paths, basenames and intent phrases the user typed ("write a report", "save to", "a separate file", "make a backup"). The Write and Bash gates can then downgrade deny to allow-with-note, or to ask, for matching targets. sprawl-guard's rule is the right default: a named file or an explicit "new version" request turns deny into confirm, but backups and protected paths stay denied ([sprawl-guard](https://raw.githubusercontent.com/nyla111/sprawl-guard/HEAD/README.md)). The override must come from the user's prompt, never from the agent's own text. pchalasani's `>allow-git` shows the shape: a token only a human types ([pchalasani](https://pchalasani.github.io/claude-code-tools/plugins-detail/safety-hooks)).

**Close the Bash write bypass before the write, not after.** The current design catches `cat > SUMMARY.md <<EOF`, `cp app.py app_backup.py`, `mv x.py x_old.py`, `tee notes.md` and `python -c "open('debug_x.py','w')"` only at Stop, after the file exists and possibly after a `git add` of explicit paths. Anthropic's docs say Read/Edit denies do not reach "arbitrary subprocesses that read or write files indirectly" ([Permissions](https://code.claude.com/docs/en/permissions)). silent-code and dcg both treat shell writes as first-class ([silent-code](https://raw.githubusercontent.com/janoppix/silent-code/HEAD/README.md); [dcg](https://raw.githubusercontent.com/Dicklesworthstone/destructive_command_guard/main/README.md)). The fix is a stdlib `shlex`-based extractor in the existing PreToolUse Bash gate. It should resolve output targets of `>`, `>>`, heredoc redirections, `tee`, `cp`/`mv`/`install` destinations, `sed -i`/`perl -i`, `touch` and `mkdir`, plus literal paths in `python -c`/`node -e` `open(..., 'w')` calls. It should see through `bash -c`, `sh -c`, `env`, `sudo`, `git -C` and `cd X &&` up to safety-net's five levels, then run the same new-file policy as the Write gate. `cp`/`mv` deserve special attention, because they are the most natural way an agent makes a backup and they slip past name-only Write checks today. Commands that are too dynamic to resolve should fail open and fall through to the Stop sweep.

**Protect the guard.** An agent that hits a deny can edit `.no-git-slop.json` to add an allow glob, run `git commit --no-verify`, which v0.1.0 already blocks, or neutralize the hooks another way: `git -c core.hooksPath=/dev/null commit`, `git config core.hooksPath`, `HUSKY=0`, `SKIP=no-git-slop`, deleting `.git/hooks/pre-commit`, or editing `.claude/settings*.json`. agent-guardrails blocks `core.hooksPath` changes, and karanb192's config-guard and conclaude's default protection cover config edits ([agent-guardrails](https://raw.githubusercontent.com/Alex-Caepio/agent-guardrails/HEAD/README.md); [karanb192](https://raw.githubusercontent.com/karanb192/claude-code-hooks/HEAD/README.md); [conclaude](https://connerohnesorge.github.io/conclaude/reference/config/pre-tool-use)). Agent edits to the policy should be **ask**, not deny, because users legitimately tune it through Claude. Config that loosens policy should also be separable from config that tightens it, following safety-net's "additive only" rule for anything the agent writes ([safety-net](https://konfuzian.github.io/claude-code-meta/docs/ecosystem/safety-tools)). The earlier research supports this independently: analyzer feedback loops have been documented gaming the analyzer, so every gate's config has to be out of the agent's reach ([Kadam](https://arxiv.org/pdf/2610.38977)).

**Recognize harness artifacts and never blame the agent for them.** Sandbox stubs, `tmpclaude-*-cwd` files and zero-byte placeholder manifests are created by Claude Code itself ([#78419](https://github.com/anthropics/claude-code/issues/78419); [#17600](https://github.com/anthropics/claude-code/issues/17600); [#46165](https://github.com/anthropics/claude-code/issues/46165)). The SessionStart baseline already absorbs those present at start. Ones created mid-session need an explicit harness allowlist: character devices and `/dev/null`-backed stubs (checked with `os.stat` and `stat.S_ISCHR`), the `tmpclaude-*` pattern, `.claude.json.backup`, and `.claude/worktrees/`. The sweep should report these separately as "harness artifacts, not yours, leave them" or ignore them. The bulk-add deny message should also mention that `git add .` fails under the sandbox anyway, which turns a nag into useful help.

**Ship framework presets instead of flagging plan folders.** Detecting framework markers (`.specify/`, `openspec/`, `docs/superpowers/`, `.planning/` or `.active_plan`, `thoughts/`, `.taskmaster/`, `.claude/epics/`, `.ralph/`, `.claude-flow/`, `.compound-engineering/`) should auto-allow that framework's conventional paths at write time ([spec-kit](https://github.com/github/spec-kit); [OpenSpec](https://github.com/Fission-AI/OpenSpec); [planning-with-files](https://github.com/OthmanAdi/planning-with-files); [HumanLayer create_plan](https://unpkg.com/humanlayer@0.17.2-npm/.claude/commands/create_plan.md); [ccpm](https://github.com/automazeio/ccpm); [ralph-claude-code](https://github.com/frankbria/ralph-claude-code); [compound-engineering](https://github.com/EveryInc/compound-engineering-plugin)). planning-with-files is the sharpest case: its `findings.md` and `progress.md` would trip a status-report rule, yet the framework gitignores them by default and depends on them. The policy decision moves to commit time. A `plans: commit | ignore | archive` setting says whether these files may be staged, and a `tidy` action can archive finished plans to `archive/YYYY-MM-DD-name/`, the convention OpenSpec and snarktank/ralph already use ([snarktank/ralph](https://github.com/snarktank/ralph)).

**Coexist with Anthropic's built-in block.** In subagents, Claude Code already rejects `report*/summary*/findings*/analysis*` `.md` writes ([#44657](https://github.com/anthropics/claude-code/issues/44657)). no-git-slop adds value where that block does not reach: the main thread, other names (`*_NOTES.md`, `IMPLEMENTATION_SUMMARY.md`, `CHANGES_MADE.md`), Bash-written reports, and commit-time staging. When hook input carries `agent_id`/`agent_type`, the plugin should use the same "return it as text in your final response" wording, so the agent never gets two contradictory instructions. The plugin must also never be stricter than the built-in in a way the user cannot turn off. Its opt-out has to be documented, settable in project config, and announced in the README, because the absence of one is the whole complaint in #101519 ([#101519](https://github.com/anthropics/claude-code/issues/101519)).

Two quieter hazards round out the list. Agent-supplied paths and commit messages are **untrusted input**. Heyosseus/sloppy had to fix code injection through unescaped file names in generated config, and world-writable settings directories ([sloppy issues](https://github.com/Heyosseus/sloppy/issues)). So the engine must never pass paths to a shell, and must write state with restrictive permissions. And the guard should not drift into designs the survey shows backfiring: LLM judges inside a blocking gate (nondeterministic, per tdd-guard's own trade-off), auto-closing or auto-rewriting history (opencommit's post-push rewrite Action is an anti-pattern), and hard-coded attribution positions.

## The best technique gates every route to disk and history against stated intent

Combining the earlier method research with this survey gives a technique with nine parts. Each part exists in some repo today; no single repo combines them.

**Know the intent.** Capture the user's prompt at UserPromptSubmit and keep a per-session record of what the user explicitly asked to create, stage or commit. Every later verdict is "slop *relative to the request*", which is the Karpathy test ("every changed line should trace directly to the user's request") applied to files ([karpathy CLAUDE.md](https://raw.githubusercontent.com/multica-ai/andrej-karpathy-skills/HEAD/CLAUDE.md)) and the condition Anthropic's own block lacks.

**Know the filesystem truth.** Take a SessionStart baseline of untracked files, re-inject a five-line reminder on compaction, verify the sanctioned scratch location is ignored, and judge only what changed since the baseline. Harness artifacts are excluded. Superpowers' "check the VCS diff, not the agent's report" is the principle ([Superpowers verification](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)).

**Gate every route to disk before it happens.** Run the same new-file policy on the Write tool, on parsed Bash writes, and on other agents' patch formats. Every block names a destination (`.scratch/`, "edit X in place", "return it as text") and an override path, so the redirect does the persuading and the deny is only the backstop. That keeps compliance high, per the earlier finding that agents obey a concretely named tool at very high rates ([Gloaguen et al.](https://arxiv.org/html/2602.11988v3)).

**Gate every route into history semantically.** Parse git commands through wrappers and pathspecs. Block bulk staging and verify bypasses. Check messages before the commit and re-check after. Gate push on unpushed violations, and run an author-side PR check that mirrors peakoss/FairPR. Everything is deterministic and stdlib, using exit codes and terse JSON.

**Sweep at Stop, once.** Compare `git status` to the baseline, block once with a single combined list of findings, then downgrade to a systemMessage when `stop_hook_active` is set. The earlier research's caution about the eight-continuation cap still applies ([Hooks reference](https://code.claude.com/docs/en/hooks)).

**Protect the guard.** Agent edits to policy, settings, hooks and CI are ask. Hook-path and skip-variable tricks are denied. Agent-written config can only tighten.

**Backstop with the same engine outside the agent.** pre-commit, pre-push and CI run the identical policy, because Codex hooks fail open on errors and humans and other agents commit too ([Codex hooks](https://learn.chatgpt.com/docs/hooks.md)). ThammanaSrinivas/guardrails states the principle: "One rule set, enforced everywhere" ([guardrails](https://raw.githubusercontent.com/ThammanaSrinivas/guardrails/HEAD/README.md)).

**Clean up after the task, separately.** From the earlier research: a test-gated minimization pass, then a fresh-context, read-only reviewer against the spec, a diff-size budget and a declared-scope check. Separate refiners cut excess changes from +242% to +4%, while self-minimization in the same context failed ([RECAP](https://arxiv.org/html/2608.13292v1)).

**Measure.** Log every gate firing and override locally, publish false-positive rates from the fixture corpus, and run the paired evaluation the earlier report designed. This survey found no competitor with a measured false-positive or stray-file rate, so evidence is itself a differentiator.

The practical slogan is that **no-git-slop should be the guard that says yes to the user and no to the agent's leftovers**. sprawl-guard proves the "yes to the user" half is buildable. The git layer, the CI parity, and the self-protection are where no-git-slop can be unambiguously best.

## What this survey cannot tell you

The limits are substantial and should temper any competitive claim. **Star counts are unverified or inconsistent.** The GitHub REST repos endpoint and `gh api` were blocked in most research threads. Counts come variously from a search-API snapshot on 2026-11-24, fetched repo pages, awesome.ecosyste.ms or third-party "best-of" lists, and they conflict. safety-net appears as about 1,294 and 2,099. Superpowers appears as 324k, 326k and "298K". Several counts look implausible for repo age (karpathy-skills ~235k, ponytail ~198k, taste-skill ~121k), and they could be inflated ([best-of list](https://ryanalberts.github.io/best-of-Agent-Harnesses/c/coding-harness-configs/)). Star counts in this report measure attention at best, not adoption or quality. **Enumeration is not exhaustive.** The `stop-hook` GitHub topic alone listed 38 repos, of which only 20 were seen ([topic page](https://github.com/topics/stop-hook)). Many small repos were judged from one-line descriptions without reading the README. Community marketplaces, Hacker News "Show HN" threads (hn.algolia.com was blocked) and Reddit were not surveyed. Several recalled repos (johnlindquist/claude-hooks, GowayLee/cchooks, trailofbits/claude-code-config and others) were never verified. **Most of the closest competitors are tiny and new.** sprawl-guard, silent-code and agent-guardrails have zero stars and no issue traffic, so their claimed behavior comes from READMEs, not from use. **Issue comments, including any Anthropic staff replies, could not be read**, so the closed state of the tmpclaude and sandbox-stub issues may mean fixed, duplicate or stale-closed. Whether hook input reliably identifies subagent context in every version is documented as "some contexts add `agent_id`", not guaranteed ([Hooks reference](https://code.claude.com/docs/en/hooks)). **The comparison table scores no-git-slop from its design description, not from a test run**, and scores competitors only on documented features. Finally, **no study measures stray-file or commit-hygiene rates for any tool surveyed here**, so every "better" in this report is a design argument, not an outcome.

## Conclusion

The survey changes where no-git-slop's effort should go. Before it, the natural roadmap was "more rules": more suffixes, more report names, more content checks. After it, rules look like the commodity layer. hookify lets anyone write them, aislop and grain already cover code and commit-message content, and Anthropic hard-codes the most obvious one. The scarce properties are judgment and integrity. Judgment means knowing what the user asked for, which files the harness made, and which folders a framework owns. Integrity means seeing writes through Bash, refusing to let the agent disable the guard, and enforcing the same policy after the session ends. Those are harder to copy than a regex list, and they are what the open complaints about Anthropic's built-in block are really asking for.

The second implication is strategic. no-git-slop's nearest rival solved the file half first and left git untouched, while the git-side tools ignore files. A tool that does both, credits sprawl-guard and pchalasani for the mechanisms it borrows, and publishes a false-positive and bypass corpus alongside its rules would be the first in this space whose claims could be checked. Because the first measured dataset on agent repo hygiene does not yet exist, shipping it with the tool is likely worth more than any single feature on the roadmap.
